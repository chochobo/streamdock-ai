# 293S 기기 검증 기록

이 문서는 초기 README에 기록한 시험 결과를 보존합니다. 날짜와 시험 범위를 확인하세요.

## 실기기 화면과 버튼

**실험 단계입니다.** 연결된 장치는 제조사 SDK에서 293s V3로 식별하는 `6603:1014`입니다. 2026년 11월 9일 실물 시험에서 사용자가 시험 화면 15개가 모두 바른 방향으로 표시된 것을 확인했습니다. 왼쪽 위와 오른쪽 아래 버튼을 눌렀을 때 앱은 각각 1번과 15번 입력을 받았습니다. 사용자는 실제 대시보드 모드에서 에이전트 상태 화면이 표시된 것도 확인했습니다. 이 모드에서 8번 키를 눌렀을 때 앱은 입력과 상태 갱신을 기록했습니다. 나머지 키의 입력은 아직 실물에서 확인하지 않았습니다.

오른쪽 화면은 표시 전용 영역 3개로 구성합니다. 작업 중·확인 필요·완료 수, 감지된 확인 필요 항목과 마지막 갱신 시각을 표시합니다. 추정 상태는 `?`로 구분합니다. 상태는 2초마다, 시각은 1분마다 확인하며 바뀐 영역만 전송합니다. 2026년 11월 9일 사용자가 실제 장치에서 오른쪽 요약 화면이 표시되는 것을 확인했습니다. 번호를 붙인 시험 화면으로 16·17·18 영역의 순서를 눈으로 확인하지는 못했습니다. 이후 사용자가 제공한 사진에서 오른쪽 화면의 왼쪽 글자가 잘린 것을 확인했습니다. 사진을 바탕으로 글자를 안쪽에 배치했습니다. 사용자는 보정 후 작업·확인·완료와 갱신 시각이 잘리지 않고 보이는 것을 확인했습니다. 정확한 물리적 표시 범위는 측정하지 않았습니다.

앱을 종료하면 장치를 놓습니다. 다시 공식 앱을 사용할 수 있습니다. 연결이 끊어지면 앱은 자동 재연결을 시도하고, 다시 연결되면 현재 화면을 다시 보냅니다. 기기 시작·재연결 시 휘발성 아이콘 초기화 명령 `CLE`와 화면 갱신 명령을 보낸 뒤, 15개 키와 오른쪽 3개 표시영역에 검은 이미지를 보내고 현재 화면을 그립니다. 이 과정은 기기에 저장된 영구 부팅 로고를 변경하지 않습니다. 2026년 11월 10일 사용자는 이 초기화 순서를 적용한 실제 293S에서 키 사이와 오른쪽 표시영역 사이의 부팅 배경이 사라지고 화면과 버튼이 정상이라고 확인했습니다. 이 결과만으로 `CLE` 명령 하나의 효과를 분리해 확인한 것은 아닙니다. 오른쪽 화면 전체를 하나의 연속된 이미지로 그리는 방법은 아직 확인하지 못했습니다.

`CLE`를 포함한 시작 초기화와 18개 표시영역은 모의 장치로 시험했습니다. 2026년 11월 10일 실제 293S에서 `node-hid`와 Swift HID 각각의 화면·물리 버튼과 USB 분리 후 자동 재연결을 확인했습니다. 검은 초기화 화면 자체는 실제 기기에서 별도로 확인하지 않았습니다. 네이티브 앱은 Swift HID를 기본으로 사용하며 `--node-hid` 실행 옵션으로 이전 드라이버를 선택할 수 있습니다. 장치가 연결되지 않으면 USB 연결, 공식 앱 실행 여부와 macOS 권한을 확인하세요. 293S V3와 Stream Dock XL 외의 모델과 USB ID는 지원하지 않습니다.

## 자동 및 실기기 시험

```sh
npm test
```

자동 드라이버 테스트는 모의 HID 장치를 사용합니다. 실제 293s V3에서는 위에 적은 시험 화면과 에이전트 상태 화면, 1번·8번·15번 버튼 입력을 확인했습니다. 2026년 11월 9일 사용자가 실제 기기의 프로젝트·세션 화면과 현재 Codex 채팅 및 활성 Claude 세션 이동을 확인했습니다. 이후 현재 계정 필터를 적용하고 버튼과 같은 앱 API를 사용해 다른 Claude 채팅에서 선택한 기존 채팅으로 전환되는 것도 확인했습니다. 이 시험은 선택한 세션에 한정되며 모든 계정과 세션의 이동을 보장하지 않습니다. 딥링크 요청 수락과 실제 채팅 선택은 다릅니다. 제한은 [세션 열기 안내](focus.md)를 참고하세요.

## Stream Dock XL

2026년 11월 20일 실제 Stream Dock XL(`5548:1028`)에서 확인했습니다(아래). 국제판 `5548:1031`은 실물로 확인하지 않았습니다. 지원하는 장치는 `5548:1028`(중국판)과 `5548:1031`(국제판)입니다. 통신 방식은 293S V3와 같고, 키 32개(4행 × 8열), 80×80 이미지, 180° 회전이 다릅니다. 근거와 출처는 설계 문서 [`docs/specs/2026-11-19-xl-support-design.md`](specs/2026-11-19-xl-support-design.md)에 있습니다.

- 배치: 아래 줄 오른쪽 4개(28–31)가 기능·사용량(또는 뒤로)·이전·다음 키입니다. 오른쪽 열의 위 세 키(7·15·23)에 293S의 오른쪽 화면과 같은 요약(작업 수·확인 필요·시각)을 표시합니다. 누르면 이동합니다(#32): 7번은 에이전트 목록 첫 화면, 15번은 확인 대기 세션 열기(여럿이면 누를 때마다 다음 세션, 없으면 오류 세션, 그것도 없으면 에이전트 목록), 23번은 사용량 화면입니다. 장면·게임 중에는 무시합니다
- 장면·게임은 원작 그림이 15키 기준이라 왼쪽 위 5×3 영역과 그 오른쪽 열 3칸에 표시합니다. 나머지 키는 비우며, 이때 요약 키도 비웁니다. 장면 종료는 3번째 줄 왼쪽에서 5번째 키(20번)를 1.2초 이상 누릅니다
- 로커(조이스틱, #8): 왼쪽 로커 위·아래는 지금 화면의 이전·다음 키, 누르기는 뒤로 키와 같습니다. 그 키가 화면에 있고 켜져 있을 때만 동작하므로 프로젝트 첫 화면에서 누르기는 아무 일도 하지 않습니다. 오른쪽 로커 위·아래는 장치 밝기를 10씩 올리고 내리며(10–100, 설정에 저장. 화면이 꺼지지 않도록 10 아래로는 내리지 않고, 밝기를 모르는 첫 조작은 50을 기준으로 한다), 누르기는 비워 두었습니다. 장면·게임 중에는 로커를 모두 무시합니다. 꾹 누르고 있어도 한 번만 동작하며, 결과는 상태 API의 `lastInput`(`control`·`action`·`code`)에 남습니다
  - 방향: 공식 SDK와 Companion의 이름이 달라(왼쪽·가운데·오른쪽 / 위·누르기·아래) 코드 `0x21`·`0x24`를 "위"로 가정했고, 2026년 11월 20일 실물(`5548:1028`)에서 로커 6개 입력의 방향이 맞는 것을 확인했습니다. 다른 기기에서 반대로 나오면 `src/device-profiles.mjs`의 `ROCKERS_XL` 표에서 `up`·`down`만 바꾸면 됩니다. 동작 연결은 `src/server.mjs`의 `ROCKER_KEYS`·`ROCKER_BRIGHTNESS_STEP`에 있습니다
- RGB LED는 쓰지 않습니다
- 293S V3와 XL을 동시에 연결하면 어느 쪽도 열지 않고 "일치하는 장치가 여러 개입니다"로 멈춥니다. 한 대만 연결하세요
- 기기가 연결되기 전의 미리보기 배치는 `STREAMDOCK_MODEL`(`293sv3`·`xl`)을 따르고, 없으면 293S입니다. 이번 실행 중 감지한 기기는 연결이 끊겨도 유지하지만, 앱을 다시 시작하면 잊습니다

실물에서 확인할 것: 32키의 위치·방향([키 시험 화면](#키-시험-화면)), 각 키 입력, 로커 6개 입력의 방향, 요약 키, 장면 1개, USB 분리 후 재연결.

요약 키 이동(#32) 실물 확인 결과(2026년 11월 22일, `5548:1028`, XL 묶음 맨 위 브랜치로 빌드한 앱): 7번은 에이전트 목록, 23번은 사용량으로 이동하고, 확인 대기 세션이 있을 때 15번이 그 세션 열기를 시도하는 것까지 확인했습니다. 에이전트 목록에서 7번을 누르면 이미 그 화면이라 변화가 없는 것이 정상입니다. 세션 열기 실패 메시지는 잠깐만 보입니다.

실물 확인 결과(2026년 11월 20일, `5548:1028`, Swift HID, XL 묶음 맨 위 브랜치로 빌드한 앱): 모델 인식과 8×4 배열·미리보기 격자, 32키의 위치·방향과 각 키 입력, 로커 6개 입력의 방향과 동작(페이지 이동·뒤로·밝기 조절, 밝기 하한 10), 제어 키(28–31)와 요약 키(7·15·23) 배치, 장면 1개의 표시 영역과 20번 키를 길게 눌러 종료, USB 분리 후 자동 재연결과 화면 다시 그리기를 모두 확인했습니다.

이때 앱 **연결과 진단**의 "마지막 기기 응답"은 계속 "기록 없음"이었고, 하트비트는 몇 초 간격으로 갱신됐습니다. XL은 쓰기 확인 보고(10번째 바이트가 `0xff`인 입력 보고)를 보내지 않는 것으로 보입니다. XL의 연결 상태는 하트비트와 재연결 칸으로 판단합니다.

## 키 시험 화면

실물에서 키 위치·방향·입력 번호를 한 번에 확인하는 화면이다(#12).

- 여는 법: `기능` → `설정` → `키 시험`
- 나가는 법: 맨 아래 오른쪽 키(293S 14번, XL 31번)를 1.2초 이상 누른 뒤 놓는다. 설정 화면으로 돌아간다. 다른 키는 오래 눌러도 나가지 않으며, 나가기 키도 짧게 누르면 시험 입력으로만 기록된다
- 각 키: 큰 글씨 위치 번호(왼쪽 위 0부터 행 우선), `r행 c열`, `slot 기기 슬롯 번호`. 나가기 키는 붉은 바탕에 `길게: 나가기`
- 누른 키: 노란 바탕으로 바뀌고 `입력 0x..`(기기가 보낸 원래 입력 코드)를 표시한다. 같은 내용이 Mac 앱 미리보기 아래 안내 문구와 `GET /api/status`의 `keyTest.last`(`index`·`code`·`row`·`col`·`slot`)에 나온다
- 293S 오른쪽 화면 3칸: 각각 `slot 16·17·18`과 마지막 키 번호 / 입력 코드 / 나가는 키·누른 횟수
- XL은 요약 키(7·15·23)도 시험 대상이다. 로커(#8)를 움직이면 동작하지 않고 Mac 앱 미리보기 안내 문구와 `keyTest.last`(`rocker`·`action`·`code`)에 기록만 한다 — 방향 확인용
- 일반 키 이미지만 보낸다. 부팅 로고·영구 저장 영역은 건드리지 않는다. 시뮬레이터 모드에서도 앱 미리보기로 같은 화면을 볼 수 있다

확인할 것:

1. 번호가 왼쪽 위 0에서 오른쪽·아래로 늘어나고, 글자가 바로 서 있다(방향)
2. 각 키를 눌렀을 때 그 키가 노랗게 바뀌고, 표시된 번호가 누른 위치와 같다
3. 입력 코드: 293S는 그 키의 슬롯 번호와 같다(예: 0번 키 = 0x0D). XL은 위치 번호 + 1(0번 키 = 0x01, 31번 키 = 0x20)
4. 293S 오른쪽 화면이 위에서부터 16·17·18 순서다
5. 나가기 키를 길게 누르면 설정으로 돌아가고, 일반 화면과 요약이 다시 그려진다

실물 확인 결과(2026년 11월 20일, Stream Dock XL `5548:1028`): 1·2·3·5번과 로커 기록을 확인했습니다. 293S V3에서는 이 화면을 실물로 확인하지 않았습니다(4번 포함).

## 키 타일 갤러리

실물 없이 잘림·겹침을 눈으로 확인하려면 갤러리 스크립트를 쓴다.

```sh
node scripts/tile-gallery.mjs
```

실제 렌더러(`keyTileSvg`, `summarySvgs`)로 프로젝트·세션·한도·막대·메모리·제어 키·알림·요약 화면을 한국어와 영어로 그린다. 짧은 이름부터 아주 긴 이름, 한중일 글자, 이모지, 경계 퍼센트(0·59·60·85·100), 오래된 값까지 포함한다. 각 예시는 293S 크기(96px)와 XL 크기(80px)로 나란히 보인다.

- 결과: `build/tile-gallery/index.html` (이미지가 data URI로 들어 있어 파일 하나로 열린다)
- 원본 SVG: `build/tile-gallery/svg/`
- 다른 위치에 쓰려면 환경변수 `TILE_GALLERY_OUT=<폴더>`
- 예시 목록은 `scripts/tile-gallery-fixtures.mjs`. 종류나 상태를 추가하면 여기에 예시도 더한다.
- 네트워크·하드웨어가 필요 없고 `build/`는 git에서 무시된다.
